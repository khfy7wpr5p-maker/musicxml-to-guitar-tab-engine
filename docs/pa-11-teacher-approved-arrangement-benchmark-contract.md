PA-11 is evaluation infrastructure only. It defines how independently teacher-reviewed polyphonic guitar arrangements may become fixed benchmark evidence for later deterministic or learned arrangement evaluation.

The central rule is:

> A benchmark case is not teacher-approved merely because it is structurally valid, generated by the engine, committed to Git, or physically playable. Teacher approval applies only to one exact immutable reviewed benchmark artifact version.

## 1. Purpose

The future `TeacherArrangementBenchmark 1.0.0` exists to provide an independent, fixed reference set for evaluating guitar-arrangement systems against explicitly teacher-reviewed outcomes.

It must not:

- produce public polyphonic output;
- select a final arrangement for normal conversion;
- modify source MusicXML;
- modify PA-4 through PA-9 authority;
- modify canonical v1 or proposed v2 semantics;
- act as a training corpus merely because it contains labels;
- infer teacher approval from engine output;
- bypass physical playability constraints.

PA-11 follows the repository's earlier fixed teacher benchmark principle: evaluation truth is separate from production authority and separate from training data.

## 2. Gate decomposition

PA-11 should proceed in separately reviewed slices:

| Slice | Scope | Authority |
|---|---|---|
| `PA-11.0` | benchmark contract and review rules | documentation only |
| `PA-11.1` | fixed proposed seed fixtures + proposed manifest | evaluation artifact only; not teacher-approved |
| `PA-11.2` | explicit teacher review of exact artifact version | converts only that exact reviewed benchmark version to teacher-approved evidence |
| `PA-11.3` | deterministic evaluation harness, if separately approved | evaluation/reporting only; no production selection authority |

Completion of `PA-11.0` does not authorize creation of teacher-approved labels.

## 3. Proposed artifact identity

Working contract identity:

```text
documentType: TeacherArrangementBenchmark
contractVersion: 1.0.0
```

A future benchmark artifact should have a stable benchmark identity and explicit review state:

```text
TeacherArrangementBenchmark 1.0.0
├─ documentType
├─ contractVersion
├─ benchmarkId
├─ benchmarkVersion
├─ reviewStatus
├─ guitar
├─ physicalPolicy
└─ cases[]
```

`reviewStatus` is exactly one of:

- `proposed`
- `teacher-approved`

No other string is equivalent.

## 4. Review/version integrity

Teacher approval binds to exact benchmark content, not to a filename or branch name.

Any material change after approval requires a new review cycle. Material changes include at least:

- fixture bytes;
- source SHA-256;
- source policy;
- case membership or ordering;
- arrangement labels;
- acceptable-arrangement membership;
- preferred-arrangement designation;
- target pitches;
- selected string/fret positions;
- selected shape/finger/barre facts;
- guitar configuration;
- physical-validation policy identity;
- pedagogical focus or scope where it changes label meaning.

After any such change, the artifact must return to `proposed` until explicitly reviewed again and must advance `benchmarkVersion` when appropriate.

A `reviewStatus: "teacher-approved"` field alone is not proof of approval. Repository governance must preserve the exact reviewed artifact identity and review evidence.

## 5. Source fixture boundary

Benchmark source fixtures must be fixed repository-local source material with explicit source policy.

Allowed source policies for the initial contract:

- `self-authored`
- `CC0`
- `public-domain`

The initial PA-11 seed set should prefer self-authored synthetic exercises so that copyright, privacy, and mutable-source risks are minimized.

A case source must record at least:

```text
source
├─ path
├─ sha256
└─ policy
```

Rules:

- path is repository-relative;
- parent traversal is prohibited;
- absolute paths are prohibited;
- backslash traversal aliases are prohibited;
- source bytes are bound by lowercase SHA-256;
- remote URLs are not benchmark authority;
- a digest proves content binding only, not copyright ownership or teacher identity.

## 6. Initial musical coverage

PA-11 should begin with small self-authored examples, not repertoire-sized scores.

The seed benchmark should eventually cover distinct arrangement problems such as:

1. two-note simultaneous intervals retained without reduction;
2. three-note chord retention with more than one physically valid guitar voicing;
3. conservative chord reduction where one source note is omitted;
4. octave displacement needed to obtain a viable guitar realization;
5. competing register-preservation choices across voices;
6. open-string versus fretted-position pedagogical alternatives;
7. barre versus non-barre acceptable realizations where both are valid;
8. repeated/sustained harmonic context where later transition evaluation is meaningful.

This list defines desired coverage, not teacher-approved answers.

Deferred from the initial benchmark unless separately reviewed:

- arbitrary orchestral reduction;
- tuplets/grace-note arrangement semantics;
- unconstrained revoicing;
- automatic arpeggiation;
- public polyphonic conversion;
- learned ranking authority.

## 7. Case model

Each benchmark case should contain exactly the information required to identify source truth, pedagogical focus, and complete acceptable outcomes.

Conceptual shape:

```text
case
├─ caseId
├─ pedagogicalFocus
├─ source
├─ sourceSelection
├─ acceptedArrangements[]
└─ preferredArrangementId
```

Rules:

- `caseId` is unique and bounded;
- `pedagogicalFocus` is bounded descriptive metadata;
- `sourceSelection` identifies the exact part/region/event set covered by the benchmark case;
- `acceptedArrangements[]` is non-empty only when the case is ready for pedagogical review;
- `preferredArrangementId` may be null;
- a preferred arrangement must be an exact member of `acceptedArrangements[]`.

## 8. Complete-arrangement labels, not independent local labels

PA-11 evaluates arrangement choices that interact across simultaneous notes and potentially across time.

Therefore acceptable labels must represent complete approved arrangements for the benchmark scope, not independent per-note labels whose Cartesian product could invent combinations the teacher never approved.

Each accepted arrangement should be a complete internally consistent outcome for the case.

This differs intentionally from the earlier monophonic fingering benchmark, where event-local alternatives were sufficient for that benchmark's narrower purpose.

## 9. Accepted arrangement identity

Each accepted arrangement has a stable unique `arrangementId` and records one complete pedagogically acceptable outcome.

Conceptually:

```text
acceptedArrangement
├─ arrangementId
├─ decisions[]
├─ noteOutcomes[]
├─ selectedShapes[]
└─ reviewNotesCode
```

`reviewNotesCode` must be a bounded controlled code or null. Free-form personal teacher commentary should not be embedded in the fixed benchmark artifact.

The benchmark contract must not require names, emails, timestamps, account IDs, or other personal identifiers to represent approval.

## 10. Arrangement decisions

`decisions[]` represents the benchmark's expected source-to-arrangement transformation for that accepted arrangement.

The decision vocabulary must stay aligned with the approved PA-4 vocabulary:

- `PRESERVED`
- `OMITTED`
- `OCTAVE_DISPLACED`
- `VOICE_REDISTRIBUTED`
- `CHORD_REDUCED`
- `REVOICED`
- `ARPEGGIATED`

However, the initial benchmark must not silently authorize runtime support for decisions that current deterministic execution still defers.

A benchmark may document future pedagogical examples for deferred decisions only in a separately reviewed benchmark version and must mark evaluator/runtime support distinctly. Evaluation fixtures do not create production capability.

## 11. Note outcomes

Every source note inside the benchmark scope must have exactly one final note outcome within each accepted arrangement.

A note outcome must distinguish at least:

- source event identity;
- governing arrangement decision;
- final disposition;
- source pitch;
- target pitch when retained/transformed;
- selected guitar position when retained;
- selected-shape reference when part of a retained simultaneous multi-note shape.

Omitted notes must not have fabricated target pitch, selected position, selected finger, or selected shape facts.

Retained notes must have one exact selected guitar position.

## 12. Selected position rules

For each retained note:

- exactly one string/fret position is recorded for a complete accepted arrangement;
- the selected position must produce the exact target MIDI under the recorded guitar configuration;
- simultaneous retained notes belonging to one selected shape must use distinct strings;
- the benchmark must not create physically impossible positions merely because a teacher prefers the musical idea.

Teacher approval can establish pedagogical acceptability only within the physically admissible domain.

## 13. Selected shape rules

PA-11 inherits the PA-10.4 selected-shape completeness invariant.

For any source simultaneous group with two or more retained members in one accepted arrangement:

- exactly one complete selected shape must represent all and only those retained members;
- every retained member must reference that selected shape;
- shape positions must use distinct strings;
- finger assignments must cover the exact retained membership;
- the shape must be compatible with the recorded physical-validation policy.

For zero or one retained member from a source simultaneous group:

- no multi-note selected shape may be fabricated;
- a retained singleton still has exactly one selected guitar position.

## 14. Finger and barre facts

Where a complete accepted multi-note shape contains left-hand fingering facts:

- open string uses finger `0`;
- fretted notes use fingers `1..4`;
- barre/partial-barre records must bind to exact affected string/fret membership;
- fingering facts describe the teacher-approved accepted arrangement, not all candidate shapes the engine considered.

The benchmark must not store PA-7/PA-8 candidate graphs as golden truth.

## 15. Physical admissibility

Teacher approval does not override physical validation.

A future artifact admitted as `teacher-approved` must satisfy both layers:

1. structural/physical admissibility under the exact recorded guitar configuration and approved physical-validation policy;
2. explicit pedagogical teacher approval of the complete arrangement.

A physically rejected PA-9 shape cannot become benchmark gold merely through a review-status string.

If the physical policy later changes materially, old benchmark approval must not silently be interpreted as approval under the new policy. Policy/version identity remains part of benchmark interpretation.

## 16. Multiple acceptable arrangements

The benchmark must support more than one teacher-acceptable complete arrangement for the same source case.

This is necessary because guitar arrangement often has several pedagogically valid solutions.

Evaluation must distinguish at least:

- exact preferred match, when a preferred arrangement is asserted;
- acceptable complete-arrangement match;
- physically valid but not teacher-approved benchmark match;
- invalid/unmatched result.

PA-11.0 defines these semantic categories but does not implement scoring.

## 17. Preferred arrangement semantics

`preferredArrangementId` may be null.

When non-null:

- it identifies one member of `acceptedArrangements[]`;
- it expresses a pedagogical first choice for this benchmark artifact;
- it does not imply that other accepted arrangements are errors;
- it must not be copied automatically from the current engine's output.

## 18. Independence from current engine selection

Golden labels must not be generated by running the current engine and declaring its selected output teacher truth.

Engine output may be shown to a teacher as one candidate during a future review workflow, but approval must remain an independent explicit act and the benchmark must preserve acceptable alternatives where appropriate.

The same fixed benchmark must not later be used both as training data and as independent evaluation evidence for the trained system.

## 19. Training-data separation

`TeacherArrangementBenchmark` is evaluation evidence, not training consent and not a training corpus.

Future learned arrangement work must use separately governed training data with its own provenance, lawful-use/privacy, consent where applicable, split integrity, model lifecycle, and leakage controls.

Benchmark fixtures and labels must not be silently copied into training and then used to claim independent benchmark performance.

## 20. Privacy boundary

The fixed benchmark must not contain:

- teacher/student names;
- account identifiers;
- emails or phone numbers;
- free-form lesson notes;
- private student performance data;
- network metadata;
- consent records;
- private lesson recordings;
- unrelated personal data.

Pedagogical approval is represented by artifact governance and review status, not embedded personal identity.

## 21. Copyright boundary

A benchmark fixture must have an explicit source policy.

For initial PA-11 artifacts, self-authored synthetic MusicXML is preferred.

No copyrighted score copy may be included merely because it is useful for testing. External mutable URLs are insufficient source authority for a fixed benchmark.

## 22. Hostile-data contract direction

A future machine-readable benchmark contract must fail closed for at least:

- unknown fields;
- symbol properties;
- non-enumerable semantic properties;
- accessor-backed fields;
- proxy-backed objects/arrays;
- non-plain objects;
- sparse/custom-property arrays;
- cycles;
- excessive object/array counts;
- duplicate IDs;
- malformed IDs;
- malformed SHA-256 values;
- unsafe source paths;
- unsupported source policies;
- malformed guitar configuration;
- invalid decision vocabulary;
- incomplete source-note coverage;
- duplicate source-note coverage;
- inconsistent target pitches;
- physically impossible selected positions;
- duplicate strings in one selected shape;
- incomplete selected-shape membership;
- invalid finger/barre facts;
- preferred arrangement outside the accepted set.

PA-11.0 does not implement this validator.

## 23. Deterministic ordering

Future benchmark artifacts must define deterministic ordering for:

- cases;
- source event references;
- accepted arrangements;
- decisions;
- note outcomes;
- selected shapes;
- finger/barre records.

Ordering must not be interpreted as ranking unless an explicit field says so.

In particular, the first accepted arrangement is not automatically the preferred arrangement.

## 24. Evaluation-only authority

A future PA-11 evaluator may compare engine output against benchmark evidence, but benchmark evaluation must not:

- alter the output being evaluated;
- feed the teacher-approved answer back into the current selection during the same run;
- replace failed output with a benchmark answer;
- change optimizer costs;
- change candidate ordering;
- change final-selection policy;
- write canonical output;
- activate a public API.

Evaluation observes and reports; it does not decide production truth.

## 25. Relationship to CanonicalTabResult 2.0.0 design

PA-10.4 defines the working minimal v2 canonical design. PA-11 benchmark labels may intentionally mirror compatible source/decision/outcome/shape concepts so that future evaluation is auditable.

However:

- the benchmark is a separate evaluation contract;
- it is not itself `CanonicalTabResult 2.0.0`;
- benchmark acceptance does not create a runtime v2 validator;
- benchmark approval does not create a runtime v2 producer;
- a future evaluator must compare through explicitly defined semantics rather than relabeling benchmark objects as canonical artifacts.

## 26. Relationship to PA-12

PA-12 is the later internal polyphonic E2E + monophonic compatibility gate.

PA-11 must not claim PA-12 evidence.

Before PA-12 starts, PA-11 should provide at least:

- an approved benchmark contract;
- a fixed proposed artifact format;
- at least one explicitly teacher-reviewed benchmark version, if pedagogical golden evaluation is required for PA-12;
- clear evaluation semantics that do not grant production authority.

## 27. Seed artifact admission rule

No PA-11 seed case may be labeled `teacher-approved` until the exact fixture and all complete accepted arrangement labels have been explicitly reviewed.

Until then:

```text
reviewStatus = proposed
```

is mandatory.

A future proposed artifact may be structurally validated and CI-tested without becoming golden truth.

## 28. Minimum teacher review packet

For each proposed case, the human reviewer should be shown enough information to make an informed pedagogical decision, including at least:

- source notation or a trustworthy rendering;
- source pitches/voices/onsets covered by the case;
- each proposed complete arrangement;
- omitted or octave-displaced notes;
- selected string/fret positions;
- selected fingering/barre facts for simultaneous shapes;
- physical-policy result;
- any intentionally deferred or unsupported transformation.

Approval should be case-by-case and version-bound.

## 29. PA-11.0 acceptance criteria

PA-11.0 is complete when independent review confirms that this contract:

- keeps PA-11 evaluation-only;
- separates structural validity, physical admissibility, and teacher approval;
- binds approval to an exact immutable benchmark version;
- supports multiple acceptable complete arrangements;
- does not infer teacher truth from current engine output;
- preserves PA-4 decision vocabulary without expanding runtime authority;
- requires exact source-note coverage per accepted arrangement;
- requires one selected position per retained note;
- inherits complete selected-shape semantics for retained simultaneous groups;
- prevents teacher approval from overriding physical impossibility;
- separates benchmark data from training data;
- has privacy/copyright/source-integrity rules;
- keeps public v1 behavior unchanged;
- does not implement v2 runtime, dispatcher, final selector, evaluator, or public API;
- passes exact-head repository CI;
- receives independent scope/architecture review;
- remains separately merge-gated.

## 30. Non-authority statement

PA-11.0 does not authorize:

- creating teacher-approved benchmark labels without explicit review;
- claiming a proposed artifact is golden evidence;
- adding runtime benchmark validators;
- adding benchmark exports to `src/index.js`;
- implementing final arrangement/fingering selection;
- implementing `CanonicalTabResult 2.0.0` runtime production;
- implementing runtime version dispatch;
- modifying `CanonicalTabResult 1.0.0`;
- changing current writers;
- changing optimizer costs or ranking;
- training on the benchmark;
- activating learned ranking;
- public polyphonic conversion;
- PA-12 E2E activation;
- PA-13 public API work;
- PA-14 adapters;
- branch cleanup;
- merge without separate Merge Approval.
