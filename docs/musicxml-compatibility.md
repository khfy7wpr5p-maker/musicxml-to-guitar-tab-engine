# TAB MusicXML compatibility validation

Status date: 2026-08-01

This document records compatibility evidence for MusicXML generated by
`serializeCanonicalTabResultToMusicXml`. It does not add alphaTab or MuseScore
Studio as production dependencies and does not change CanonicalTabResult or
fingering decisions.

## Scope and tested fixtures

The compatibility suite uses two independent fixtures:

- `tests/fixtures/canonical-tab-single-note.golden.musicxml`
  - one quarter-note C4
  - standard notation staff and TAB staff
  - selected position: string 2, fret 1
- `tests/fixtures/compatibility/canonicalTabCompatibilityFixture.js`
  - five measures, including an implicit pickup
  - 12 notes and 2 rests on each rendered staff
  - whole, half, quarter, eighth and 16th durations
  - dotted half note
  - beam begin, continue and end values
  - tie start and stop
  - natural, sharp and flat pitches
  - open strings and fret 10
  - selected C4 position string 3, fret 5
  - C4 alternative string 2, fret 1, which must not affect output

The larger MusicXML fixture is generated reproducibly without writing to the
repository:

```bash
node tests/compatibility/generateCompatibilityMusicXml.js > /tmp/canonical-tab-compatibility.musicxml
```

## Validation layers

### Static repository validation

```bash
npm ci --ignore-scripts
npm test
```

The standard test suite verifies:

- well-formed UTF-8 XML
- no DTD, ENTITY or external URL output
- score-partwise structure
- one guitar part with two staves
- standard G-clef staff
- six-line TAB-clef staff
- standard guitar tuning
- measure, event and rhythm order
- pitch, octave, duration, type, dots, ties and beams
- selected string and fret
- no string or fret data on rests
- deterministic output and input immutability

### alphaTab importer validation

The compatibility workflow installs one exact alphaTab version only inside the
isolated CI workspace. The package is not added to `package.json` or
`package-lock.json`.

```bash
npm ci --ignore-scripts
npm install --no-save --package-lock=false --ignore-scripts @coderline/alphatab@1.8.4
ALPHATAB_EXPECTED_VERSION=1.8.4 node tests/compatibility/alphaTabMusicXmlSmoke.mjs
```

The smoke test runs on Node.js 18, 20 and 22. It checks the imported alphaTab
model rather than only checking that parsing returned without an exception.

Observed alphaTab 1.8.4 result:

```json
{
  "tracks": 1,
  "staves": 2,
  "measures": 5,
  "notesPerStaff": 12,
  "restsPerStaff": 2,
  "tuning": [64, 59, 55, 50, 45, 40],
  "firstSelectedPosition": { "string": 3, "fret": 5 },
  "doubleDigitFret": true,
  "tieOriginsPerStaff": 1,
  "explicitBeamBeatsPerStaff": 10,
  "synchronizedPlaybackStarts": true
}
```

The test also imports the small golden single-note fixture and confirms string
2, fret 1.

### MuseScore Studio validation

The local execution environment and the GitHub-hosted Ubuntu runner were
checked for these command names without installing software:

```text
MuseScore4
musescore4
mscore4
musescore
mscore
```

No MuseScore CLI was available. Therefore MuseScore import, visual inspection,
MusicXML re-export, semantic round-trip comparison and PDF export were not
executed. This is an environment limitation, not evidence of either
compatibility or incompatibility.

When MuseScore Studio is available in an isolated environment, the official
command-line export form can be used with safe process arguments:

```text
MuseScore4 --no-webview --no-synthesizer --export-to <output.musicxml> <input.musicxml>
```

The round-trip comparison must be semantic. Metadata, XML element order and
layout changes must not be treated as musical data loss.

## Findings and classification

### No confirmed writer defect

- Severity: none
- Affected tool: alphaTab 1.8.4
- Fixture: both fixtures
- Expected: importer preserves the tested semantic data
- Actual: all importer assertions passed on Node.js 18, 20 and 22
- Root cause: not applicable
- Smallest solution: no production change
- Production code change required: no

### alphaTab ignores `staff-type` but still detects the TAB staff

- Severity: low
- Classification: alphaTab importer behavior / MusicXML interpretation
- Affected tool: alphaTab
- Fixture: compatibility fixture
- Expected: the second staff is interpreted as tablature
- Actual: alphaTab source ignores `staff-type`, but `staff-tuning` causes the
  second staff to be configured as tablature; runtime import produced two
  staves with the correct tuning and positions
- Root cause: alphaTab derives tablature behavior from tuning information rather
  than the `alternate` staff type
- Smallest solution: retain the standards-compliant `staff-type`, TAB clef,
  staff lines and staff tuning combination
- Production code change required: no

### MuseScore runtime and round-trip are unavailable

- Severity: medium evidence gap, not a product defect
- Classification: working-environment limitation
- Affected tool: MuseScore Studio
- Fixture: both fixtures
- Expected: import, visual inspection and semantic round-trip
- Actual: no MuseScore executable was present locally or on the GitHub runner
- Root cause: tool unavailable and installation was outside the approved scope
- Smallest solution: run the documented test in an isolated environment that
  already contains MuseScore Studio
- Production code change required: no

### Visual rendering and active-cursor UI are not exercised

- Severity: low-to-medium evidence gap
- Classification: working-environment limitation / unverified behavior
- Affected tool: alphaTab
- Fixture: compatibility fixture
- Expected: visible notation, visible TAB, fret 10 and cursor movement
- Actual: importer model, display flags, positions and synchronized playback
  starts were verified; no browser or Skia renderer was instantiated
- Root cause: this milestone deliberately avoids production rendering
  integration and extra graphics dependencies
- Smallest solution: a later isolated renderer-level smoke test
- Production code change required: no

## Production changes

No production source file was changed during compatibility validation. In
particular:

- `src/writers/canonicalTabMusicXmlWriter.js` was not changed
- selectedPosition behavior was not changed
- alternativePositions remain non-authoritative for rendered TAB
- no candidate generation or optimizer call was added
- no alphaTab or MuseScore production dependency was added

## CI workflow

`.github/workflows/musicxml-compatibility.yml` runs:

- pinned alphaTab 1.8.4 importer tests on Node.js 18, 20 and 22
- a non-installing MuseScore CLI availability probe

The existing `Tests` workflow continues to run the complete repository test
suite on Node.js 18, 20 and 22.

## Future polyphony boundary

The current evidence applies only to the existing monophonic CanonicalTabResult
contract. Chords or independent voices would require explicit canonical event
identity for simultaneous notes, chord grouping, multiple voice timelines,
voice-aware backups/forwards, tie identity across voices and a revised MusicXML
staff/voice mapping. None of those changes are part of this validation
milestone.
