# TAB MusicXML Compatibility Validation

Status reviewed: **2026-08-10**

This document records repeatable compatibility evidence for MusicXML generated by `serializeCanonicalTabResultToMusicXml`.

Compatibility tools do **not** become production dependencies or authority over `CanonicalTabResult`, selected positions, candidate generation or fingering.

## Current verdict

**Partially validated — strong alphaTab rendering/cursor evidence; MuseScore and production playback/PDF evidence still open.**

Verified:

- static MusicXML and repository contract tests pass;
- real alphaTab 1.8.4 MusicXML import passes;
- real alphaTab SVG rendering passes in Node.js;
- real alphaTab browser rendering and external-media cursor pass in headless Chrome;
- the browser artifact demonstrates standard notation, six-line TAB, double-digit fret rendering, ties, beams and cursor overlays for the compatibility fixture;
- the latest LR-S1B.2b pull-request compatibility run (#297) completed successfully without changing writer semantics.

Not yet verified/implemented:

- alphaTab production synth/player readiness;
- real MuseScore Studio import;
- MuseScore MusicXML re-export;
- MuseScore semantic round-trip;
- MuseScore/PDF export;
- production application score/TAB viewer;
- production PDF viewer/print/share.

No current evidence identifies a TAB MusicXML writer defect.

## Authority boundary

The intended downstream architecture is:

```text
CanonicalTabResult 1.0.0
        ↓
TAB MusicXML
        ├─→ alphaTab
        │    ├─ import validation
        │    ├─ score/TAB rendering
        │    ├─ bar/beat cursor
        │    └─ future playback adapter
        │
        └─→ MuseScore
             ├─ independent import validation
             ├─ professional engraving check
             ├─ semantic round-trip
             └─ optional PDF / Print
```

Neither alphaTab nor MuseScore may recalculate or replace engine fingering authority.

- verifies notation and TAB visibility;
- checks tuning and fret-10 model/rendered text;

The captured compatibility artifact demonstrates:

The screenshot is evidence for the fixture/environment only and is not a pixel-perfect regression contract.

## Measure and beat cursor status

Cursor support has two separate statuses:

1. **Compatibility technology:** verified in the headless alphaTab browser test.
2. **Production application feature:** not implemented yet.

A future application viewer may therefore reuse the verified cursor model, but it still needs explicit application-state tests for:

- current measure/bar;
- current beat;
- seeking;
- playback synchronization;
- pause/resume;
- stop/reset;
- end-of-score behavior;
- repeated user actions and cleanup.

## alphaTab synthesizer / playback diagnostic

The synth diagnostic remains intentionally non-authoritative.

In the tested alphaTab 1.8.4 + headless Chrome environment, synthesizer mode did not reach ready state. The browser reported an internal recursive `loadedMidiInfo` stack error before score/MIDI/SoundFont/player readiness completed.

Because the same MusicXML imports, renders and drives the external-media cursor successfully, this remains classified as an alphaTab synth/runtime or environment interaction rather than a demonstrated writer defect.

Do **not** claim production playback readiness from current evidence.

Before Play/Pause/Stop is implemented in a product UI, require a separate gate that verifies:

- supported/pinned alphaTab/player runtime;
- score readiness;
- MIDI readiness;
- SoundFont/audio readiness where applicable;
- deterministic start/seek/pause/resume/stop behavior;
- cursor/audio synchronization;
- repeated-load cleanup;
- browser lifecycle/resource cleanup;
- failure isolation from core conversion.

## MuseScore semantic round-trip gate

The future MuseScore gate must compare musical meaning, not raw XML bytes.

Minimum semantic comparison:

- measure count/order and visible measure identity where meaningful;
- note/rest ordering;
- pitch step/alter/octave or equivalent normalized pitch;
- duration/divisions semantics;
- note type and dots where preserved;
- time signatures;
- ties;
- beams;
- standard/TAB staff structure;
- guitar tuning;
- selected string/fret technical data.

Formatter-specific XML ordering, generated IDs or irrelevant layout serialization should not fail the gate unless they alter musical meaning.

## MuseScore process-security requirements

If a future adapter executes MuseScore, define the process boundary before production use:

- approved executable discovery and supported-version policy;
- no shell command construction;
- fixed executable + controlled argument array;
- no arbitrary user-supplied CLI flags;
- isolated temporary working directory;
- canonicalized input/output paths;
- symlink/path-traversal controls where relevant;
- execution timeout and termination policy;
- bounded stdout/stderr capture;
- bounded output file size;
- concurrency ceiling;
- cleanup in success and failure paths;
- clear stable error codes;
- core conversion remains valid if rendering fails.

OS/container-level CPU/memory controls may be required for a truly bounded external renderer; Node process invocation alone is not a complete resource sandbox.

## PDF status

PDF is not a current core output implementation.

Safe future path:

```text
validated CanonicalTabResult
       ↓
TAB MusicXML
       ↓
validated MuseScore/renderer adapter
       ↓
PDF artifact
       ↓
PDF validation
       ↓
application PDF preview / print / download / share
```

PDF is derived presentation output. It must not become source truth and must not cause valid JSON/ASCII/MusicXML conversion to fail merely because an external renderer is unavailable.

## Musical notation compatibility coverage

Current verified input/output/rendering coverage includes:

- whole / half / quarter / eighth / 16th;
- dotted values;
- rests;
- ties;
- beams;
- pickup measures;
- time signatures/divisions;
- selected guitar string/fret data.

Current parser still rejects or does not explicitly model separate future notation areas including:

- slur/legato;
- grace notes;
- tuplets;
- 32nd and later advanced rhythm values;
- ornaments;
- additional articulations/expressive marks.

Future notation work must add parser/canonical/writer/alphaTab/MuseScore round-trip tests explicitly rather than weakening fail-closed validation.

## Independent real-world MusicXML E2E gap

Repository-generated/golden fixtures provide strong deterministic coverage but are not the same as independent producer evidence.

A separate future E2E gate should use a legally/provenance-safe MusicXML fixture created independently of this engine and verify:

```text
independent MusicXML
    ↓
preflight / parse
    ↓
CanonicalMusicDocument
    ↓
physical candidates
    ↓
deterministic optimizer
    ↓
CanonicalTabResult
    ↓
TAB MusicXML
    ↓
alphaTab import/render
    ↓
MuseScore import/round-trip when available
```

The independent fixture must remain fixed and content-bound once accepted as regression evidence.

## Compatibility evidence limitations

- passing compatibility tests do not prove compatibility with every MusicXML producer;
- a screenshot proves the tested fixture/environment, not general engraving correctness;
- alphaTab renderer success does not prove synth/playback readiness;
- current CI does not prove MuseScore compatibility because MuseScore was not executed;
- current evidence does not prove production PDF generation;
- compatibility tools do not gain canonical authority;
- production application UX still requires separate application E2E.
